# Personas and Journeys

## 1. 핵심 페르소나(재정의)

### Persona A. AI (자동 발주 주체)
- 정의: API 키로 인증되어 Human Proxy에 작업을 자동 등록/검토 요청하는 소프트웨어 에이전트
- 상황:
  - AI가 스스로 완료할 수 없는 오프라인/판단형 작업이 발생
  - 요청 지연 시 상위 워크플로우 전체가 지연
- 목표:
  - 작업을 빠르게 등록하고, 결과를 신뢰 가능한 형태로 수신
  - 승인/반려 결정을 API 이벤트로 일관 처리
- 실패 요인:
  - 인증 실패, 멱등성 누락, 웹훅 실패
- 성공 지표:
  - 작업 등록 성공률, 검토 리드타임, 웹훅 성공률

### Persona B. AI 도입 담당자 (의뢰 운영자)
- 정의: 자신의 AI 또는 업무 자동화에 Human Proxy를 붙여 운영하는 사람
- 상황:
  - 비개발 또는 준개발 사용자로, GUI 중심 운영 선호
  - 비용 통제와 결과 품질 모두 중요
- 목표:
  - “무엇을 원하는지”와 “합격 기준”을 명확히 정의
  - 승인/반려 결정을 빠르게 수행하고 비용을 예측 가능하게 관리
- 실패 요인:
  - 홈/대시보드에서 다음 행동 불명확
  - 등록 폼 과복잡, 정책 이해 비용 과다
- 성공 지표:
  - 작업 등록 완료율, 승인 결정 시간, 예치금 부족 이탈률

### Persona C. 인간 작업자
- 정의: 플랫폼에서 작업을 수락하고 제출 후 정산받는 수행자
- 상황:
  - 다수 작업 중 기준이 명확하고 지급 안정성이 높은 작업을 선호
- 목표:
  - 수락 전에 합격 기준을 명확히 이해
  - 제출 후 승인/정산 상태를 예측 가능하게 확인
- 실패 요인:
  - 모호한 기준, 반려 사유 불명확, 정산 일정 불투명
- 성공 지표:
  - 수락 전환율, 재제출 성공률, 정산 성공률

## 2. 공통 Journey 구조
- Discover: "이 서비스가 뭔지" 10초 내 이해
- First Action: 역할별 첫 CTA 실행
- Core Loop: 등록 → 수락 → 제출 → 검토/승인 → 정산
- Repeat Loop: 결과 품질 개선과 비용 최적화

## 3. 페르소나별 Journey 상세

### 3.1 AI Journey
1. `API 인증 설정`: 키/서명 규칙 적용
2. `작업 등록`: 프롬프트, 합격 기준, 보수, 기한 전송
3. `상태 수신`: OPEN/CLAIMED/SUBMITTED 이벤트 추적
4. `검토 결과 반영`: APPROVED/REVISION/REJECTED 처리
5. `정산 확인`: settlement 이벤트 수신 및 내부 상태 동기화

### 3.2 AI 도입 담당자 Journey
1. `랜딩 진입`: 제품 목적 이해
2. `의뢰 시작 CTA 클릭`: 작업 생성 화면 진입
3. `작업 등록`: 목표/기준/보수/기한 입력
4. `검토함 처리`: 승인/수정요청/거절 결정
5. `지갑 확인`: 예치/정산/환불 상태 확인

### 3.3 인간 작업자 Journey
1. `일감 탐색`: 보수/기한/기준 비교
2. `작업 상세 확인`: 합격/금지 기준 확인
3. `수락`: 작업 시작
4. `제출`: 텍스트/증빙 업로드
5. `정산 확인`: 대기/지급/실패 상태 추적

## 4. 구체적 User Flow (MVP)

### 4.1 AI Flow
`/api-docs` 또는 `/ai/dashboard`
-> `새 작업 등록`
-> `작업 상태 확인`
-> `검토함`
-> `승인/반려`
-> `지갑/정산 확인`

예외 분기:
- 인증 실패 -> 키/서명 점검 화면
- 웹훅 실패 -> 재전송 화면

### 4.2 AI 도입 담당자 Flow
`/`(랜딩)
-> CTA `의뢰 시작하기`
-> `/owner/tasks/new`
-> 등록 완료
-> `/owner/reviews`
-> 승인/수정요청
-> `/owner/wallet`

예외 분기:
- 잔액 부족 -> 충전 유도
- 분쟁 발생 -> `/owner/disputes`

### 4.3 인간 작업자 Flow
`/`(랜딩)
-> CTA `작업 시작하기`
-> `/worker/jobs`
-> `/worker/jobs/[taskId]`
-> `작업 수락`
-> `/worker/submissions/[submissionId]`
-> `/worker/earnings`

예외 분기:
- 반려 -> 재제출
- 지급 실패 -> 재시도/분쟁

## 5. CTA 설계 원칙(기획 반영)
- 랜딩: 역할별 1차 CTA를 첫 화면에서 바로 노출
- 대시보드: "오늘 해야 할 일" 기준 CTA 2개 이상 고정
- 모든 핵심 페이지: 다음 행동 버튼이 스크롤 없이 보여야 함
- 상세 정책/기술 정보는 하위 페이지로 분리하여 정보 과적재 방지
